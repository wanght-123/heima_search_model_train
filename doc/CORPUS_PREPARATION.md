# 微调语料准备与发布说明

## 1. 目标

语料准备的目标不是单纯增加条数，而是让每条样本都能回答一个明确问题：模型应该在什么输入下，依据什么业务规则，稳定输出什么结果。

本项目包含两种训练数据：

- **SFT 数据**教会模型“正确答案是什么”。
- **DPO 数据**教会模型“两个看似合理的答案中为什么更偏好其中一个”。

DPO 不能代替 SFT。模型尚未掌握任务、schema 或分类体系时，应先补 SFT；模型已经能做但在边界、幻觉、格式或偏好上反复出错时，再考虑 DPO。

## 2. 通用原则

### 2.1 先规则，后标注

每个任务先固定：

- 输入范围和不属于本任务的内容；
- 输出字段、类型、空值和字段顺序要求；
- 抽取字段的证据规则；
- 分类标签全集、层级路径和近邻标签边界；
- 冲突、缺失、歧义和无法判断时的处理规则；
- 是否允许解释、Markdown、思维过程或额外字段。

规则仍在频繁变化时，不要大规模标注。先用 50～100 条标定集让标注者达成一致，再扩量。

### 2.2 正确性优先于数量

错误标签会被模型直接学习。以下样本不得因“接近正确”而放行：

- 输出无法解析或字段类型错误；
- 抽取值没有原文证据，或把推断当事实；
- 分类标签不在候选体系内或层级路径非法；
- 同类输入执行了相互冲突的规则；
- chosen 与 rejected 都可接受，偏好无法稳定判断；
- 输入、输出或元数据包含不应进入训练的敏感信息。

### 2.3 覆盖真实分布，也覆盖高价值长尾

数据集应同时覆盖：

- 真实线上高频任务与字段；
- 影响业务较大的低频错误；
- 短文本、长文本、噪声文本、口语化输入和缺字段输入；
- 空值、否定、冲突、多实体、近邻标签和边界案例；
- 不同来源、行业、城市、岗位和表达方式。

不要通过机械复制或同义改写制造虚假规模。重复模板会让离线指标看似提升，却降低真实泛化能力。

### 2.4 可追溯与合规

每条原始样本至少保留 `sample_id`、`source_id`、任务名、来源批次、规则版本和标注版本。数据发布前确认来源授权、使用范围、保留期限和脱敏要求。

姓名、手机号、身份证号、详细住址、聊天账号等非任务必需信息应删除或不可逆脱敏。不要把 API 密钥、内部凭据、未授权网页内容或模型系统提示写入训练语料。

## 3. 防止数据泄漏

切分必须按信息来源分组，而不是随机拆单条样本。本项目使用 `source_id` 切分：同一招聘原文派生出的抽取、分类等多任务样本必须全部进入同一个 split。

推荐集合职责：

| 集合 | 用途 | 是否可用于调参 |
| --- | --- | --- |
| train | 参数更新 | 是 |
| dev | 训练内评测、早停、checkpoint 选择 | 是 |
| diagnostic | 错误分析和开发期快速验证 | 是 |
| frozen_test | 最终业务验收 | 否 |

还应执行近重复检查。对输入进行规范化后计算 hash，并结合文本相似度排查跨集合的模板化近重复。冻结测试集的输入、答案以及由其生成的改写样本，都不得进入同轮 SFT 或 DPO 数据。

## 4. SFT 语料准备

### 4.1 推荐结构

项目使用 LLaMA-Factory ShareGPT 格式。单条 SFT 样本示意：

```json
{"conversations":[
  {"from":"system","value":"任务规则和输出 schema"},
  {"from":"human","value":"业务输入"},
  {"from":"gpt","value":"{\"field\":\"正确值\"}"}
]}
```

要求：

- system 明确任务和输出约束，但避免堆叠互相冲突的规则。
- human 保留真实业务表达，不在输入中泄漏答案。
- gpt 只包含最终业务答案；本项目是 JSON 任务，不加入解释、Markdown 或思维链。
- 同一任务的字段类型、空值表达和 schema 保持一致。
- 非空抽取值可以回指输入证据；标准化值符合允许的映射规则。

### 4.2 数据配比

先按任务和关键错误类型统计，再决定是否补样本。不要简单把所有任务凑成相同数量；应结合线上流量、业务损失和当前错误率确定权重。

如果某类样本占比很低但后果严重，可以适度过采样；过采样后的同源或近重复样本仍必须只在 train 中，不能污染 dev/test。

### 4.3 SFT 质检

至少包含三层：

1. **程序检查**：JSONL 可解析、必需字段存在、角色顺序正确、schema/类型/枚举合法。
2. **规则检查**：证据 span、分类路径、空值、否定和边界规则正确。
3. **人工抽检**：按任务、来源、长度和困难类型分层抽样，不只随机看容易样本。

对关键任务建议双人独立标注和仲裁。记录一致率，并把高争议规则返回标注规范，而不是只改当前样本。

## 5. DPO 语料准备

### 5.1 推荐结构

项目使用 ShareGPT ranking 格式：

```json
{"conversations":[
  {"from":"system","value":"任务规则和输出 schema"},
  {"from":"human","value":"业务输入"}
],
"chosen":{"from":"gpt","value":"{\"field\":\"正确值\"}"},
"rejected":{"from":"gpt","value":"{\"field\":\"有明确目标错误的值\"}"}}
```

### 5.2 偏好对原则

每一对都必须满足：

- chosen 按当前规则可证明正确；
- rejected 足够像真实模型错误，而不是无意义乱码；
- 每对只有一个主要错误，非目标部分尽量相同；
- 两者长度、语气、键顺序等表面特征尽量平衡；
- 能用一句稳定的业务规则解释为什么 chosen 更优；
- 两个答案不能都可接受，也不能 chosen 仅因“写得更长”获胜。

优先从已通过隔离要求的模型错误分析中提取错误类型，再生成新的偏好输入或使用允许的训练来源。不要直接把冻结测试集错误改成训练 pair。

### 5.3 DPO 数据拆分

DPO train/eval 也要按 `source_id` 或等价来源键分组切分。DPO eval 只用于训练内偏好 loss 和 checkpoint 选择，不能替代独立 SFT 格式的冻结业务测试集。

详细的错误码、困难负样本和发布门禁见 [`DPO_DATA_DESIGN_PLAN.md`](DPO_DATA_DESIGN_PLAN.md)。

## 6. 推荐生产流程

```text
业务目标与指标
  → 规则/schema/taxonomy 定版
  → 来源清点与脱敏
  → 50～100 条标定集
  → 扩量标注或受控生成
  → 程序校验
  → 分层人工复核与仲裁
  → 按 source_id 防泄漏切分
  → 去重、分布和 token 长度分析
  → 生成 dataset_info.json 注册
  → 冻结 manifest、hash 和版本号
  → 小模型训练验证
  → 错误分析后决定补 SFT 还是 DPO
```

## 7. 发布清单

数据版本进入训练前，逐项确认：

- [ ] 规则、schema 和 taxonomy 有明确版本且已冻结。
- [ ] 来源、授权、脱敏和保留策略已确认。
- [ ] 所有 JSONL 可逐行解析，编码统一为 UTF-8。
- [ ] SFT 角色和 DPO ranking 结构符合 LLaMA-Factory 注册。
- [ ] 抽取值、枚举值、字段类型和空值通过程序检查。
- [ ] chosen 与 rejected 不同，且偏好理由唯一明确。
- [ ] train/dev/diagnostic/frozen_test 按 `source_id` 隔离。
- [ ] 已完成精确重复和跨集合近重复检查。
- [ ] 按任务、来源、长度、标签和错误类型输出分布报告。
- [ ] tokenizer 后长度分布已检查，截断比例在可接受范围内。
- [ ] 人工抽检覆盖高风险与长尾样本，问题已闭环。
- [ ] 数据文件、`dataset_info.json`、manifest、hash 和生成脚本一起归档。

## 8. 训练后如何反哺语料

错误分析先区分原因，再决定数据动作：

| 错误原因 | 优先动作 |
| --- | --- |
| 任务或 schema 尚未学会 | 增补高质量 SFT |
| 标签规则本身含糊 | 先修规则并重新仲裁，不急于训练 |
| 两个合理输出之间偏好不稳定 | 构造最小差异 DPO pair |
| 长文本截断 | 调整数据裁剪或 `cutoff_len`，不能只复制样本 |
| 某来源/任务过拟合 | 去重、调整配比并扩大来源覆盖 |
| 冻结测试集发现错误 | 记录为下一版本需求；当轮不得回填训练集 |

每轮只改变少量可解释因素，并保留上轮数据 manifest 与评测结果，才能判断提升来自数据、参数还是随机波动。
